# F-014 — Сквозная проверка и локальные логи

Дата создания/обновления: 2026-10-05. Приоритет: MVP. Статус: in_progress. Дизайн/приёмка: автор; документация/реализация: Codex. Модель проекта: premium (D-006). Карточка определяет поведение и приёмку; TBD закрываются перед затронутой реализацией.

Текущее состояние: Созданы и запущены первые EditMode/PlayMode проверки и локальные отчёты. Тесты готовки/полного выпуска, структурированный игровой лог, Windows-сборка и внешний плейтест впереди.

Связи: [индекс](../feature-index.md), [решения](../decisions.md), [проверки](../test-plan.md), [полный GDD](../../GAME_CONCEPT.md), [инструкция Unity](../../CODEX_PROJECT_INSTRUCTIONS.md). Источники: GDD §21–22; инструкция §20.

## Проблема, цель и ожидаемый эффект

Отличать написанное от работающего и обнаруживать причины сломанных повторов/переходов.

Почему сейчас / выбранный объём: Проверки должны идти с первого запуска, иначе интеграционные проблемы видны слишком поздно. verified требует наблюдаемый результат, а не наличие файлов. Критерий успеха — наблюдаемое выполнение acceptance ниже; количественный плейтест интереса оценивается на игровом срезе по GDD §22, а не по наличию файлов.

## Игровое поведение и сценарий

Каждый этап получает реальные сценарии проверки и запись результатов. Локальный лог фиксирует попытку/seed/версию/ключевые факты/итоги, без per-frame шума. Полный выпуск и Windows build проверяются перед статусом готового MVP; затем внешний плейтест.

Первый вход и повтор используют эти же правила; чистый повтор и новые/прежние seeds определяются штатным Restart/Retry, а не визуальной анимацией.

## In / Out / Future

EditMode/PlayMode/manual по рискам, validator, отчёты вне Assets, локальные логи, Development/release проверка, диагностический плейтест. Без облачной аналитики/автотестов, которые только повторяют реализацию.

## Зависимости и место в выпуске

Старт с F-001; финальная приёмка F-001…F-013. Полная готовность фичи требует её полного scope; ранняя часть в вертикальном срезе отдельно отмечается в журнале.

## Данные и параметры

playtest_participants=5–10; proposed_nonempty_submit_rate=0.8, proposed_causality_rate=0.7, proposed_retry_rate=0.5 — ориентиры GDD, уточнить до внешнего теста. Версия баланса/seed обязательны в отчёте.

Значения «старт GDD» являются редактируемыми предложениями. Прямые решения D-001…D-007 имеют приоритет. Невалидные конфиги должны давать понятную диагностику, а не случайный результат.

## События и локальная проверка

show_started, round_started/ended, dish_submitted/judged, reaction_started, elimination_resolved, final_winner_revealed, retry/restart; версию/контекст фиксировать без скрытого изменения результата.

Дизайн-ключи здесь не требуют отдельной строковой системы событий; техническое сопоставление берётся из инструкции. Локальный лог с контекстом/seed достаточен; серверная аналитика не входит в MVP.

## UI и тексты

Debug может показать диагностические данные; обычная игра их не требует. Результат проверки — краткий отчёт автора и запись в implementation-log.

## Негативные случаи и ограничения

Editor недоступен, тест частично пройден, forced результат, зависшая presentation, ошибка логирования. Непроверенное явно названо; debug overrides не выдаются за естественный проход.

## Acceptance criteria

1. С первого этапа существует план и фактический журнал; необходимые checks проходят перед verified.
2. Проверены инварианты еды, pause/timeup, Skip, roster, seed, anonymous mapping, Retry/Restart.
3. Полный обычный выпуск и отдельная Windows-сборка проверены; debug отделён.
4. Плейтест собирает причинность/удобство/повтор/длительность и ведёт к документированному решению об улучшении.

## Способ проверки и анализ

Канонический набор T-001…T-026 в ../test-plan.md; доказательства/ограничения в ../implementation-log.md.

После проверки записать pass/fail, контекст/seed, ограничения и доказательство в implementation-log, обновить статус в индексе. Если критерий не пройден, исправить затронутую часть перед зависимой фичей; успешный статический осмотр не заменяет Play Mode.
